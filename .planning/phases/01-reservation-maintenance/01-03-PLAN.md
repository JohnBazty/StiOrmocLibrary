<objective>
Give librarians the Reservations tab on /librarian/maintenance to view and save the pickup window and the waiting-list limit, and remove the fixed-hours wording from the Book queue page.

Purpose: SPEC R7 (screen part) for RES-MAINT-01 and RES-MAINT-02, and the web part of SPEC R8. The API from plan 01-01 does all validation; this screen shows values, sends what the librarian typed, and shows the server's message.
Output: ReservationSettingsPanel with tests, two client calls, the tab entry, and updated Book queue wording.
</objective>

## Artifacts this phase produces

- Component `ReservationSettingsPanel` in `apps/web/src/features/reservations/ReservationSettingsPanel.tsx` with test file `ReservationSettingsPanel.test.tsx`.
- Client calls `reservationApi.settings()` (GET) and `reservationApi.saveSettings(body)` (PUT) to `/api/v1/admin/reservation-settings`, and exported type `ReservationSettingsView` in `apps/web/src/features/reservations/reservation-api.ts`.
- Tab key `reservations` labelled "Reservations" in `CatalogMaintenancePage`.
- Book queue success and header text without a fixed duration.

## Planner decisions recorded here

- One Save per setting (matches the API: a key present means that setting is saved, and each setting has its own "Last changed by").
- The screen sends the typed text as is (blank for an empty limit) and relies on the API's validation and field message, so the rules live in one place (SPEC R7: invalid values are rejected with a field message and nothing is saved).
- The Book queue page is also used by Staff, who cannot read the settings API (Librarian only), so its wording names the pickup timer without a duration instead of fetching the window.

- `GET /api/v1/admin/reservation-settings` returns `data: ReservationSettingsView`.
- `PUT /api/v1/admin/reservation-settings` body `{ pickupWindowDays?: string | number; waitingExpiryDays?: string | number | null }` (a key present means that setting is saved; blank or null limit means off) returns the updated `ReservationSettingsView`.
- `type ReservationSettingsView = { pickupWindowDays: number; pickupWindowChangedBy: string | null; pickupWindowChangedAt: string | null; waitingExpiryDays: number | null; waitingExpiryChangedBy: string | null; waitingExpiryChangedAt: string | null }`
- Errors: 422 `RESERVATION_SETTINGS_INVALID` with a user-safe message ('Enter a whole number of days from 1 to 7.' or 'Leave blank to turn off, or enter a whole number of days from 7 to 90.'), 503 `RESERVATION_SETTINGS_UNAVAILABLE` before migration 043 is applied.
- The existing `request<T>()` helper in reservation-api.ts throws `ReservationApiError(message, code)` with the server message.
