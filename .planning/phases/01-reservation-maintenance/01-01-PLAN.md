## Planner decisions recorded here

- Schema gate: the schema-push contribution keys on `supabase/migrations/*.sql`; this repo uses `database/supabase/`, and project rules forbid running migrations against a live database without Ethan's go-ahead. No push task is injected. The false-positive risk it guards against is covered by running the real 043 SQL on PGlite in the tests, and by the missing-table fallback. Applying 043 is Ethan's step after review (SPEC Boundaries, out of scope).
- Each setting is saved on its own (PUT body carries one or both keys; a key present means that setting is saved). This keeps a separate "Last changed by" per setting (R7) and makes "every save of the limit restarts the count" (SPEC interview round 2) apply only when the limit itself is saved.
- No `row_version` check on save: SPEC AC 17 wants the last committed save to win, not a stale-write error.
- `apps/api/src/core/schema-readiness.ts` is not changed: listing the new table there would make `/api/health` report 503 before 043 is applied, which the SPEC deploy-before-migration constraint forbids.
