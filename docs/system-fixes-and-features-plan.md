# System fixes and features plan

- **Date created:** 2026-09-25
- **Date last updated:** 2026-09-26
- **Status:** `inprogress`
- **Scope:** The 31 distinct fixes and features requested for the deployed library system

## Why

The deployed site has reported failures in reservation, clearance, fines, printing, lost-book reporting, attendance, and category management, while several administrative and student workflows are incomplete. The updated bug list also asks for book archiving, a lost-book quote and charge, and institutional-email registration. This plan sequences repairs before new features and defines how to verify each change without damaging live library records. Phases 1 and 3 and Phase 2 item 1 are implemented and deployed. Phase 2 item 2 awaits the user's go-ahead.

## Current implementation and constraints

- The React app and Express API are live on Vercel with Supabase Postgres. All planned features and deployment checks must use Supabase Postgres as the active database; local MySQL remains an inactive rollback reference only. The latest MySQL reference migration is `20260926_042_phase2_user_management.sql` (next `043`); the applied Supabase tree reaches `011` (next `012`). Reconcile the hosted migration ledger's unrecorded `002`/`005` definitions before any whole-directory replay.
- Category create/edit/delete and reassignment already exist at `/admin/categories`, but the current table does not show every field required by the preserved product draft (category ID, description, date added). Extend and verify that workflow instead of building a second one.
- The student dashboard already renders one published announcement when the API supplies it. Verify display and refresh after a real announcement is published; scheduled publication still depends on a durable job runner.
- Student lost-book reporting, staff confirmation/rejection, copy-condition auditing, print-supply PDF reporting, and notification storage already have API foundations. The requested work should complete and connect those paths.
- Student lost-book submission creates a pending report and an admin notification. Phase 1 now adds a visible Admin clearance worklist for pending reports, with a direct link to borrower review. The live response includes that worklist; a real production report and staff decision still need controlled acceptance.
- Some books have a supplier quotation and others have no known price. A quotation is optional catalog evidence, not a required book price. Store uploaded quotations privately in Supabase Storage, keep their metadata and history in Postgres, and never expose the supplier document as a public book cover.
- The API already has an archive action for a book title, and Admin inventory has a book-copy archive action. Phase 3 A9 should expose those retained records through a dedicated Admin Book archive page and navigation item rather than create a second archive state. A permanently deleted historical record may only be visible through an existing audit snapshot; it must not be presented as a restorable archived book.
- New Student registration currently uses school ID and a generated placeholder email for the linked user. The document's `@ormoc.sti.edu.ph` note needs a decision on whether a real school email is mandatory and verified, or optional.
- Printing and fine payments currently create digital records and PDFs called receipts. The requested invoice change must preserve those historical records and must use the school's approved invoice format and numbering before the system claims to issue a BIR invoice. Printing fees and fine/lost-book collections may need different accounting treatment; the school finance team must classify them. [BIR Revenue Regulations No. 7-2024](https://bir-cdn.bir.gov.ph/BIR/pdf/RR%20No.%207-%202024.pdf) identifies invoices as primary sale documents, while the [BIR Authority to Print service](https://www.bir.gov.ph/BIRCC-RDO-External-Service-15) describes invoice authorization requirements.
- The deployed Vercel function does not start the existing one-minute reservation-expiration, overdue, or notification workers. Semester transitions and closing-time checkout must not depend on in-process timers in a serverless function.
- The preserved product draft has a configurable 5:00 p.m. default closing time. The user's current requirement is **7:00 p.m. Asia/Manila** on open days; update the configured schedule and its documentation during the attendance phase. Keep closed days and any authorized special hours configurable.
- `accounts` and `users` both carry account status. Lifecycle changes must update both consistently and preserve borrowing, fine, attendance, and printing history. A signed JWT remains valid until expiry unless authorization checks account state or token version.
- Book-copy availability and physical condition are separate. A borrowed copy reported lost needs the existing loss/charge workflow; an idle missing copy uses inventory condition auditing. Neither path should silently erase a loan or payment history.
- The current printing form only requests a quote for 1–50 copies, and the API applies the same 50-copy limit. At 60 copies, the page count and price disappear without explaining the limit. Phase 2 item B9 addresses this quantity limit; Phase 3 item P2 remains responsible for automatic document page counting.
- The interactive floor-plan editor and viewer currently supply shelf data used by category and inventory workflows. Phase 3 F1 retires their user-facing controls and mutation endpoints, but preserves the existing layout, version, event, and shelf records for future development. Essential shelf labels and assignments must remain usable through category/inventory workflows after the floor-plan editor is removed.

## Roadmap by phase

### Phase 1 — Repair the reported bugs before adding workflows

1. **Reserve button (B1)** — reproduce the failure for an unavailable title, trace the API and Postgres query/transaction, and repair the reservation path.
   - **Done when:** One click creates one queue position; duplicate requests, the Student two-book cap, and no eligible copy produce clear responses rather than HTTP 500. Faculty policy is preserved.
2. **Student clearance Refresh (B2)** — trace the click, request, recomputation, and displayed `checkedAt` value. Add visible loading/error feedback.
   - **Done when:** After a return, payment, or authorized override, Refresh shows the current standing and balances without a full page reload.
3. **Admin Record Cash Payment (B3)** — reproduce with an unpaid fine, then verify payment allocation, idempotency, payment-record creation, balance, and clearance update in one transaction. A10 separately changes the customer-facing document type.
   - **Done when:** A valid payment succeeds once and produces a viewable payment record; duplicate clicks, overpayment, and invalid amounts cannot double-charge or corrupt balances.
4. **Printing Pages/Copies fields (B4)** — allow a temporary empty input while typing; validate and normalize only on blur/submit.
   - **Done when:** Users can select and erase the current value, type a new one, and see the recalculated price; empty, zero, and out-of-range values cannot be submitted.
5. **Fine adjustment Audit Reason (B5)** — reproduce typing in the waiver/void modal, fix any focus/state interference, and verify server validation.
   - **Done when:** The full reason can be typed, remains visible until submission, and is saved in the audit record; short or missing reasons are rejected.
6. **Student Report Lost (B6)** — trace the existing button through the lost-book API and database transaction.
   - **Done when:** The owner can submit one pending report for an active loan and sees its status; the pending report appears promptly in an obvious Admin worklist or alert with the correct borrower and book; staff can open it and confirm or reject it without duplicate charges or lost inventory state. Verify the student-to-admin handoff on the deployed site.
7. **Readable attendance Time In (B7)** — compare stored timestamps with the API and display them in `Asia/Manila`; use one consistent 12-hour formatter on the dashboard, today's check-in card, attendance history, and admin views. Show a plain label such as “Checked in today at 1:22 PM” instead of a raw database time like `13:22:36.137655`.
   - **Done when:** The example raw time `13:22:36.137655` appears to the user as `1:22 PM`, without seconds or fractional digits. A known check-in time displays correctly with AM/PM across student and admin screens and around midnight; the deployed site shows the same readable format.
8. **Category management server error (B8)** — reproduce the “An unexpected server error occurred” banner on the Admin Category management page, identify whether it appears on load or after Add, Edit, Delete, or Reassign, and trace the failing API request and Supabase query. Repair the failing action without changing existing category assignments.
   - **Done when:** The Admin page loads without an unexpected error; Add, Edit, Delete, and Reassign either complete and refresh the directory or show a clear validation message. Verify the affected action on the deployed site with a dedicated test category. The Phase 2 category-field and presentation enhancements (A2) remain separate.

### Phase 2 — Admin, catalog, reservation, and finance workflows

1. **User management (A1)** — add profile editing and Activate/Deactivate/Archive actions to the current read-only directory. Restrict fields and roles, record actor/reason/time, synchronize `accounts` and `users`, and invalidate existing access appropriately.
   - **Done when:** Authorized staff can make each change; inactive users cannot sign in or start new library activity; old loans, payments, print jobs, and attendance remain available to staff.
2. **Category management (A2)** — after the Phase 1 server-error repair, add missing category ID, description, date-added, and book-count presentation from the product draft.
   - **Done when:** The Admin page lists and edits one canonical category record; deleting an assigned category is blocked or follows an explicit reassignment flow.
3. **Print supplies stock export (A3)** — expose the existing supply report on the supplies page and add a current-stock export if the report only contains expense history.
   - **Done when:** Admin downloads an accurate snapshot of ink bottles and paper reams, units, low-stock indicators, and timestamp; export numbers match the visible stock.
4. **Every book copy in details (A4)** — extend the book overview response and UI with one row per active copy, including accession/barcode, availability, condition, and shelf. Keep administrative QR credentials private.
   - **Done when:** A multi-copy title shows each copy's distinct state, while title-level totals still agree with the copy list.
5. **Admin Report Lost (A5)** — place an action on the relevant circulation/inventory row and route it through the existing audited workflow.
   - **Done when:** For an active loan it creates or confirms a loss report and connects to the quotation-based replacement charge in A8; for an idle copy it marks condition Lost and availability Unavailable; duplicate action is safe.
6. **Remove book purchase pricing (A6)** — remove the purchase-price input and display from book cataloging. Let the librarian optionally upload a supplier quotation for a book that has a known replacement price; books without one remain valid catalog entries marked “No quotation.” Preserve historical monetary records, but stop using the old purchase-price field for new lost-book charges. Printing-service pricing is separate.
   - **Done when:** A book can be added or edited with or without a quotation; no book-price number is requested or shown in the catalog; an authorized librarian can view and replace a quotation while its earlier versions remain auditable; a new lost-book charge cannot silently fall back to the old purchase price on the deployed site.
7. **Durable job-runner foundation (T1)** — choose a scheduled execution path that continues running on Vercel/Supabase, with authentication, locking, idempotency, metrics, and failure alerts. Move the existing notification, reservation-expiration, and overdue scans to it before releasing reservation status notifications.
   - **Done when:** Expiry and other scheduled jobs run after deployments and idle periods, can be retried safely, and expose last-success/error status to admins.
8. **Simple reservation status actions and notifications (A7)** — keep one clear next action on each admin reservation: Approve, Mark ready for pickup, or verify the physical pickup at the desk; show Cancel only while allowed. Display the current status and next step plainly, confirm cancellation, and block invalid or duplicate changes. On every successful transition, send the student or faculty member one in-app notification with the new status and any pickup deadline: Pending, Approved, Ready for pickup, Claimed, Cancelled, or Expired. Create each notification with its status change; scheduled expiry uses the durable job runner above.
   - **Done when:** Staff can update a reservation without choosing from a confusing status list; the user's reservation view and notification agree after each action. A failed or retried change does not create a false or duplicate notification, and a pickup still requires desk verification.
9. **Quotation-based lost-book charge (A8)** — when a book is reported lost, show the librarian any quotation already attached to that book. The librarian checks that it is suitable for replacing this copy and confirms the quoted amount; a newer quotation may be uploaded for this loss if needed. If the book has no quotation, show “Awaiting quotation” to staff and student and allow the librarian to upload one later. The system creates the payable replacement charge once from the approved quotation after staff confirms the loss, with the exact quotation and amount snapshotted on the report. If no quotation can be obtained, require a documented non-monetary resolution or authorized waiver rather than inventing a price. Reading a machine-readable quote may prefill the amount, but staff must confirm it; scanned or unclear documents require manual verification.
   - **Done when:** A lost book with a valid quote produces one matching charge and links to the quote used; a book without a quote has no guessed or zero-value charge while awaiting a quote; a rejected report creates no charge; a revised quote does not silently change an existing charge. The student's clearance and Admin view show the correct status and amount, and duplicate clicks or retries cannot create a second balance. Verify quoted, unquoted, and rejected cases on the deployed site.
10. **Invoices instead of customer-facing receipts (A10)** — replace the current receipt wording and PDFs for transactions that the school's finance team classifies as invoiceable, including printing services. Use the school's approved invoice issuer details, document format, serial-number range, and approval or permit details. Preserve existing payment and receipt rows as historical audit records; introduce backward-safe invoice records and link them to the underlying transaction rather than renaming old database tables or reissuing old documents. For collections that finance classifies differently, use an appropriately named internal payment acknowledgment rather than a tax invoice.
   - **Done when:** An authorized staff member can issue and reprint a correctly numbered invoice for an eligible transaction only after the approved invoice setup is configured; the student can view it; duplicate payment retries cannot issue a second invoice; voids/corrections retain an audit trail; older receipts remain accessible with their original labels. The deployed site never presents an unapproved PDF as a BIR-compliant invoice.
11. **Printing quotes for 60 or more copies (B9)** — raise the current 50-copy limit in both the student form and API to an agreed, safe maximum that includes at least 60 copies. Keep the quote active while the user edits copies, and show a clear range message when a quantity exceeds the approved maximum instead of silently blanking the pages and cost. Recalculate sheets and cost on the server from the detected page count and copy count; check whether the larger request needs a staff or supply warning without silently changing its price.
   - **Done when:** On the deployed site, 60 and 100 copies of a valid PDF each show the document page count, total sheets, and correct price before submission, and the saved request matches the quote. Empty, zero, non-whole, and above-limit values show a specific message and cannot be submitted; staff views and reports show the same quantity and total.

## Release and verification gates

1. **Before each phase:** reproduce the reported case against a safe local/test identity, capture the API response and deployment log, and identify whether the fault is in the interface, API, or Postgres dialect. Do not use a successful GET as proof that a write flow works.
2. **Schema changes:** reconcile the hosted Supabase migration ledger first; add versioned Postgres migration(s) starting at `010` and backward-safe MySQL rollback migration(s) starting at `041` only where needed. Backfill and preserve historical rows.
3. **Per change:** test success, invalid input, unauthorized role, duplicate/retry, and transaction rollback. For money, loan, attendance, and account-state changes, verify related records remain consistent.
4. **Before deployment:** pass API/web suites and builds, then exercise each changed workflow against a hosted Supabase test environment using test accounts. Confirm the required Postgres migrations, production configuration, durable file storage, and scheduled jobs are ready for that phase. The active app must report the Postgres driver; a missing Supabase connection must fail clearly instead of silently switching to MySQL.
5. **Live-site acceptance:** deploy the web and API changes together, apply reviewed Supabase Postgres migrations in order, and verify each phase's relevant actions at the public Vercel URL with authorized test accounts. Check both student and admin roles, actual writes and reads, notifications, images/uploads where relevant, and deployment logs. A local success alone does not mark an item complete.
6. **After deployment:** monitor errors and data consistency, remove temporary test records safely, and keep a rollback route for the application version and backward-safe schema changes. Record the deployed version and verification result in implementation tracking.
7. **Deployment order:** ship Phase 1 first. In Phase 2, deliver T1 before A7 so reservation expiry and its notifications work on the live site. Phase 4 uses that same scheduler for semester and attendance jobs. P1 should not wait for the periodic worker. Keep Phase 5 separate from the operational repairs. N1 is outside this release.
